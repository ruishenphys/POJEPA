## 3. 设计

### 3.1 续算接口

参数与 v7 粒子场景的 `System.variant_trajectory(tid, v, *, controls, start, state, ticks)` 相同：从 tick = start 的状态出发，下达动作 `controls` 经 `applied_ticks`（增益、延迟、执行噪声、饱和），推进 ticks 个 tick，返回 [ticks+1, …]。

- **push**：可续算状态就是隐藏状态 (c_x, c_y, b_x, b_y, θ)。`Push.trajectory` 的循环从 `range(TICKS)` 改成 `range(start, stop)`，默认值时完全相同。
- **gray_scott**：隐藏状态（U、V 各池化到 16×16，加注入点，514 维）不能续算，所以 `variant_trajectory` 返回完整状态 `GrayScott.pack(U, V, p)` = [U 展平 128², V 展平 128², p]，共 32770 维；`hidden()` 把它池化成 514 维，`draw()` 从它画画面。`fields()` 改写成 `start_state()`（初值 + 烧入）+ `advance(0, 32)`，算术顺序不变（§5.2 跨树逐位相同）。
- 两个场景共同的检查：`v` 必须等于当前数据集的调节项（新场景的下达动作和随机流按当前数据集取，不一致会静默拿错）；start > 0 必须给状态；0 ≤ start ≤ start+ticks ≤ 32。
- 从整条轨迹第 start 帧的状态续算，结果与整条轨迹逐位相同（浮点运算序列相同）。

### 3.2 反事实探针

新场景走 `variant_trajectory` 分支（没有 v6 原实现，基础场景也走）：真实终点 = 整条仿真第 start+τ 帧，反事实终点 = 从第 start 帧换 donor 的下达动作续算 τ 个 tick，画面带 tick 重画。整条仿真每条轨迹只算一次（gray_scott 约 5 秒）。`*_px` 列：push 是推杆和方块中心 4 个坐标的 L2 × 48（朝向角不是长度，不计入）；gray_scott 是 U、V 池化场 512 维的 L2（同 advection_diffusion 的写法，注入点有周期回绕，不计入）。

### 3.3 部分帧的像素噪声

原来 `compose`、`draw_fields`、`_finish` 按画的帧数抽噪声：整条 33 帧时第 t 帧用第 t 份，只画 1 帧时用的是第 0 份。探针和规划重画单帧时，画面噪声和数据集里那一帧不一样（而且所有重画的帧噪声相同）。现在 `pixel_noise(g, σ, shape, ticks)`：整条且不给 ticks 时就是原来那一次抽取（逐位不变）；给了 ticks 时抽整条 [33,…] 再取这几帧；部分帧不给 ticks 报错。代价是单帧重画多抽 33 倍的正态数（约 0.1 秒）。只影响带 `pixel_noise` 的探针和规划，v7 的任务表里没有这种任务。

### 3.4 规划

“状态误差”的摘要：粒子类场景照旧是受控小球位置，advection_diffusion 照旧是平均浓度场；gray_scott 是 U、V 池化场（512 维），目标与“不动”的差按场的范数的 5% 判（同 advection_diffusion）；push 是方块位姿 (b_x, b_y, size/2·θ)，要把方块推到目标，推杆不算。

push 另有两处不同：
- **目标动作**：随机动作很少碰到方块（S20a 实测约 1/3 的整条轨迹推动了方块，8 个 tick 里更少）。push 的目标动作每 2 个 tick 一段，方向 = 起点时推杆指向方块中心的方向 ± 30° 内均匀，幅值 ∈ [0.25, 0.5]，同样要求方块位姿与“不动”差 ≥ 0.15（最多重抽 20 次）。
- **真值规划代价**：用完整状态 (c, b, size/2·θ) 到目标状态的距离。只看方块时，推杆碰到方块之前代价处处相同，CEM 无从下手。模型规划的代价本来就是到目标画面（推杆也在里面）的特征距离，所以两者都瞄准“目标状态”，评分只看方块。

其他场景的目标动作、代价、随机流消耗和以前逐位相同（`goal_controls` 的非 push 分支就是原表达式，有测试）。

### 3.5 评测协议

训练只在基础场景上。每个协议只动一类变量（CausalWorld 的写法），P13 把物理、执行、观察叠在一起；P0 是分布内（基础场景测试段）。

| 类别 | 协议 |
|---|---|
| 物理 | P1 物理参数 A、P2 物理参数 B、P3 过程噪声 |
| 执行（模型看不到） | P4 增益、P5 延迟、P6 饱和 |
| 动作分布 | P7 采集策略（goal、mixed） |
| 观察 | P8 外观、P9 静止干扰光点、P10 会动的干扰光点、P11 像素噪声、P12 遮挡 |
| 组合 | P13 = P1 + P4 + P8 的同一档 |

三档强度：轻、标准、重；延迟只有 1、2 两档（整数 tick），采集策略只有 mixed、goal 两档。某个场景不适用的协议由 `variants.validate` 判定（场方程没有光点、没有受控点；push 不加过程噪声）。

- 分布外评测（`make_v8_jobs --stage variants`）评标准档：82 个测试格，每个评 6 个条件。v7 的 30 个测试调节项都是其中的标准档，目录名也相同，v7 编码好的变体测试集可以复用。
- 强度曲线（`--stage strength`）评轻档、重档：152 个测试格。
- 规划只在 P0 上（7 个场景 × 6 个条件）。

强度的取值依据：物理参数在 `variants.PARAMS` 的范围内，标准档沿用 v7 的值，重档多数取到范围边上；执行和观察项的标准档沿用 v7（增益 2、延迟 1、棋盘背景加白色、2 个干扰光点、像素噪声 10），新调节项按同样的幅度取。这些值是可以改的设计选择，改了只动 `protocols.py`，表和任务自动跟着变。

### 3.6 v8 任务表

`make_v8_jobs.py` 的段和命令写法与 `make_v7_jobs.py` 相同（A 编码、B 汇总、C 标定、C2 检查、D 训练、E 汇总；V1–V5），区别：场景是 `protocols.SCENES`（7 个）；正式阶段每个场景都跑动作探针；变体表来自协议；新增 `--stage strength`、`--protocols`、`--conditions`；默认目录 `../features-v8`、`../results-v8`。

真值规划参照的样本数：新场景每个 tick 的真值仿真贵得多（gray_scott 约 60 ms、push 约 30 ms，粒子类约 3 ms），按默认 64 个样本，identity 那条规划任务要占着 GPU 跑 4–8 小时，所以 v8 任务表给 gray_scott `--oracle-samples 16`、push `--oracle-samples 32`。push 用 32 个样本实测能把方块推到目标附近（§5.4）。

## 4. 为什么已有条件不变

- 数据生成：`fields()` 拆分后浮点运算序列不变；`Push.trajectory` 默认参数时循环不变；`pixel_noise` 在整条 33 帧、不给 ticks 时就是原来那一次 `g.normal(0, σ, shape)`。§5.2 跨树对照逐位相同。
- v7 场景的探针和规划：只多了 advection_diffusion 重画时传 tick（无像素噪声时画面不变），规划的随机流消耗、目标、代价对 v7 场景不变；`render=False` 只是不画不用的画面。
- `make_v7_jobs.py`、`make_addon_jobs.py` 没动。
