## 3. 接口和产物

- `prepared/<片>/<uuid>.npz`：04 §3 的九个数组（`numpy.savez`，先写 `.partial` 再换名）。
- `prepared/<片>/<uuid>.json`（`cache._write_json`，字节固定）：04 §3 的字段，另有 `schema: droid_prepared_v1`、`limits`、`source` 里的 numpy/scipy 版本；`checks` 每项 `{passed, …数值}`。
- `prepared/<片>/_complete/<配置名>.json`：`{schema: droid_prepare_complete_v1, shard, config, config_sha256, splits_sha256, uuids, prepared_sha256（与 uuids 对应的 JSON SHA）, counts: {episodes, passed_/failed_ 两种动作源}, code_commit}`。
- `prepared/action_scale.json`：顶层 `realized`、`commanded` 各 `{position, rotation, gripper}`（S01 读取方的格式，`droid_control_spec` 直接能读）；记录类键 `schema`、`pool`（规则、条数、splits SHA、每条准备 JSON 的 SHA）、`quantile`、`algorithm`、`episodes`/`excluded`（每种动作源用到和去掉的 uuid）、`values`（每组的数值个数）。
- `prepared/windows/<split>.json`：06 §3 的格式（`droid_windows_v1`）。
- `prepared/stats/<配置名>.json`、`prepared/_complete/stats-<配置名>.json`。

## 4. 实现上自己定的（规格没写死、可逆）

1. **数组无法构造的回合**（h5 结构不对，或视频帧数超过 h5 步数）只写 JSON，`rows`/`arrays_sha256`/`frame_sha256` 为 null，不写 npz、删掉旧的；算不了的检查记 `passed: null`，不进 `reasons`，但两种动作源都判没通过。
2. **非有限位姿**：取帧位置上有 NaN/inf 时这个动作源的周期动作整段记 NaN（不调 `poses_to_diffs`，否则 scipy 报 SVD 不收敛），`action_bounds_<源>` 判失败；JSON 里的数值只记有限值，非有限的计数。
3. **检查范围**：`finite` 核全部 T 步（状态、指令的 7 维都要有限，状态夹爪在 [0, 1]，两端都含）；`video_size` 核每一帧的形状和 uint8；`timestamps` 核全部步严格递增、每个周期间隔在 [0.8, 1.6] 秒（两端都含）；动作界两端都含。h5 用到 6 个数据集（04 §4 原文的“7 个”是笔误，已改），时间戳要有符号整数，`skip_action` 是 bool 或整数。
4. **统计按配置分文件**：04 §6 原写 `prepared/STATS.json` 和配置无关，但各片在试跑和正式运行下的回合列表不同，所以改成 `prepared/stats/<配置名>.json`（可重算，重跑覆盖）；失败比例按本配置的 `action.source`，门槛 3%（Jerry 2026-11-10 定，原 1%），恰好 3% 不算超；超了先写统计再报错，不写动作尺度、窗口和完成记录。06 §1 的引用一并改了。
5. **共用文件**（动作尺度、三份窗口）：不存在就写；已存在就重算并要求逐字节相同，不同就报错（试跑和正式运行的回合池、测试片相同，所以第二次必然相同）。`use_failures: false` 的配置只核这几个文件在、记的 `splits_sha256` 是本数据根的，不重算。
6. **跳过规则**：JSON 在、两个源文件 SHA 等于 `DOWNLOADED.json`、片名一致、有数组时 npz 在、该有 s5 帧 SHA 时有，才跳过；`limits`（取帧和检查用到的配置值）不同直接报错，一个数据根不能混两套口径。原始文件已删而输出缺失或过期：报错。准备要求本配置的 `download/<片>` 已完成且 uuid 列表一致；统计要求每片完成记录在，并核每条准备 JSON 的 SHA。
7. **s5 帧 SHA**：只给三片测试的划分列表前 `test_extra_episodes` 条（按位置，不看是否通过；附加回合是其中通过的那些，06 §3）。
8. **进程池用 spawn**（父进程有 HTTP 和 OpenCV 线程时 fork 不安全），每个进程 `cv2.setNumThreads(1)`；1 个和 2 个进程写出的 JSON 逐字节相同。
9. **窗口**：哈希相同时按起点或编号再排；`val.json` 留文件头（`schema`、`split`、`salt`、`splits_sha256`、`prepared_sha256`）加 `windows`、`counts`；`prepared_sha256` 含没通过的回合；原始帧率窗口的时长由 `frame_rate_total_frames / frames_per_interval` 推出（= 4）。CEM 的“排第 1”取该（回合，时长）哈希顺序的第一个窗口；规划窗口不够 63 个干扰项、某时长只有一条回合（没有替身）都报错。

## 6. 验证到哪一级

CPU 验证（Python 3.12.3、numpy 2.4.3、torch 2.11.0+cpu、scipy 1.16.3、PyYAML 6.0.3、h5py 3.15.1、opencv-python-headless 4.13.0.92、pytest 8.4.2），外加真实数据小样本。

- **本段测试**：`tests/test_droid_prepare.py` 79 过（设 `PO_JEPA_DROID_GOLDEN_RAW` 时含 5 个金标准测试），`tests/test_droid_windows.py` 12 过。
- **金标准回合**：5 条回合的原始文件从存储桶取（项目文件夹 `po-jepa-s05/fetch_golden.py`），frame_index、state、两种动作、command、capture_ms、第 0/15/30/V−1 帧 SHA 全部逐位相同。
- **故意改坏（C8）**：61 处单独改坏，抓到 60 处（`po-jepa-s05/mutate_s05.py`、`mutate_s05_result.txt`）。第一轮漏 2 处，补测试后抓到“窗口用 passed_commanded”；剩 1 处等价：动作尺度回合池写成 `splits.train_order(splits, data)`，只在 `use_failures: true` 分支里算，这时它就是完整训练顺序。
- **真实数据小样本**：13 个实验室各 3 条入选回合（`po-jepa-s05/real_sample_*`）：38/39 通过，每条 0.5–4 秒（单进程），周期间隔 1.017–1.101 秒，最大位移 0.29 m、转角 0.82 rad，都远在界内。1 条（RAIL+c3d50939…）`video_frames` 失败：视频 439 帧 = h5 步数（不是 T−1）。
- **视频帧数抽查**：另 260 条（各实验室 20 条，只下 MP4 读帧数，`po-jepa-s05/frame_count_survey.*`）：257 条 V = T−1，各 1 条 V = T、T−2、T−3。合起来 299 条里 4 条（约 1.3%）帧数不符。按现在的规则这些回合被跳过，而 04 §6 的“任一片失败超过 1% 任务失败”在正式运行大概率会触发。**Jerry 2026-11-10 定**：帧数不符的回合照旧跳过，门槛改成 3%（S05-fix1，`seg/S05-fix1-threshold`）。
- **全量回归（C9）**：rebase 到 f8860cf 后 2852 过、134 跳过、4 个本机无 cu130 的 test_delivery 预期失败（rebase 前在 a057dbd 上 2813 过，同样 4 个）；MANIFEST 重算后不变（170 个文件），SOURCE_MAP 0 个新候选，`verify_bundle()`、`verify_fixed_protocol()` 通过。
