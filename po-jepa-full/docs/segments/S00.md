### 3.4 双树对照冒烟 `tests/addon_dual_tree.py`

开发机专用脚本：同一台机器上要同时有 v7 树（仓库根目录）和新树。不被 pytest 收集（见 §3.3），模块顶层只导入标准库和 torch，**不导入 `po_jepa`**（父进程不能和任何一棵树绑定）；不定义 `test_*` 函数。

#### 3.4.1 命令行

```bash
cd $NEW && $PY -B tests/addon_dual_tree.py --workdir /tmp/s00-dual-tree            # 完整跑一遍
cd $NEW && $PY -B tests/addon_dual_tree.py --compare <A 的输出目录> <B 的输出目录>    # 只比较两份已有结果
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--workdir DIR` | 必填（完整模式） | 必须不存在，且不在任何一棵树里面（防止特征和结果落进仓库） |
| `--v7-tree PATH` | `Path(__file__).resolve().parents[2]`（仓库根目录） | v7 树 |
| `--new-tree PATH` | `Path(__file__).resolve().parents[1]`（`po-jepa-full`） | 新树 |
| `--sequential` | 关 | 默认两个子进程并行；加上就先 v7 后新树。并行时要求 `os.cpu_count() ≥ 2`，否则报错。跑的时候机器上不要有别的重计算（别的进程抢核只会变慢，不改结果；但不要为了快去加线程，见下） |
| `--compare A B` | — | 不跑，只比较 `A`、`B` 两个子进程输出目录（每个目录下有 `worker.json` 和 `smoke/`），用于复核和审核时的灵敏度检查；只读，结果打印到标准输出（不同之处最多列 200 条），不写文件 |

**线程数固定为 1，不设命令行参数**（脚本常量 `THREADS = 1`）。实测 v7 树自己在多线程下就不能逐位复现：同一份假特征、`PYTHONHASHSEED=0`，2 线程或 4 线程连跑两次，`calibration.yaml` 的 λ 就不同；4 线程下 po_jepa_full 的 20 个每步记录里有 86 个字段不同、60 个验证文件里 40 个不同、`model_state` 不同。1 线程加 §3.4.2 第 3 步的环境变量，两个进程同时跑，po_jepa_full 的标定、20 步每步记录、60 个验证文件、`model_state`、两次评测各 560 行和评测汇总全部逐位相同（只有 §3.4.5 列为不比的 `checkpoint_sha256`、`seconds` 不同）；vjepa2_ac_small 和按 §3.4.4 缩小的 vjepa2_ac 也一样（每步记录、验证、`model_state`、评测 560 行和汇总逐位相同）。多线程下两棵树出现的不同分不清是代码造成的还是线程调度造成的，所以不提供多线程选项。

内部还有两个只给自己调用的模式：`--worker`（§3.4.3）和 `--make-ac-checkpoint`（§3.4.4）。

退出码：逐位相同为 0；有任何不同或任何一步失败为 1。最后一行打印 `双树对照：逐位相同（…各项数量…）` 或 `双树对照：发现 N 处不同（见 <workdir>/dual-tree-report.json）`。

#### 3.4.2 流程

0. **前置检查** `preflight_checks(v7_tree, new_tree, workdir, parallel=…)`，按下面的顺序，每条失败都报错退出，各有一条单元测试（§3.5）：
   0. 并行模式下 `os.cpu_count() ≥ 2`。
   1. `--workdir` 不存在，且不在任何一棵树之内。
   2. 两棵树的路径解析后不相同。
   3. 各自有 `src/po_jepa/runtime/workflow.py` 和 `tools/smoke_v7_cpu.py`。
   4. 两棵树的 `tools/smoke_v7_cpu.py` 逐字节相同（否则输入就不同了）。
   5. v7 树是 git 检出，且 `git -C <v7> diff --quiet 911bc09 -- src configs reference tests tools run.py pyproject.toml DATASET.md MANIFEST.json SOURCE_MAP.json` 成功、`git -C <v7> status --porcelain -- <同样的路径>` 为空（v7 树必须就是冻结的 911bc09）。
1. **假特征**（和 `smoke_v7_cpu.py` 文档字符串里的用法相同，用 v7 树的编码工具，只生成一次，两棵树读同一份）：
   ```
   <PY> -B <v7>/tools/encode_v7.py encode   --system van_der_pol --trajectories 40 --output <workdir>/features --device cpu --fake-encoder
   <PY> -B <v7>/tools/encode_v7.py finalize --system van_der_pol --trajectories 40 --output <workdir>/features
   ```
   实测约 25 s，约 0.9 GB（40 条 × 33 帧 × 256 × 1408，float16）。
2. **缩小的“官方”AC 权重**：`<PY> -B <new>/tests/addon_dual_tree.py --make-ac-checkpoint <workdir>/fake-ac/vjepa2-ac-reduced.pt --tree <v7>`（§3.4.4；子进程，环境同第 3 步）。
3. **两个子进程**，各跑一棵树：
   ```
   <PY> -B <new>/tests/addon_dual_tree.py --worker --tree <T> --features <workdir>/features \
        --ac-checkpoint <workdir>/fake-ac/vjepa2-ac-reduced.pt --output <workdir>/<name>
   ```
   `<name>` 是 `v7` 和 `full`。工作目录 `cwd=<T>`。环境变量（脚本常量 `WORKER_ENV`，第 1、2 步的子进程也用）：复制当前环境，删掉 `PYTHONPATH`、所有 `PO_JEPA_*`、所有 `OMP_*`、`MKL_*`、`KMP_*`，再设
   ```
   PYTHONHASHSEED=0  PYTHONDONTWRITEBYTECODE=1
   OMP_NUM_THREADS=1  MKL_NUM_THREADS=1  OMP_DYNAMIC=FALSE  MKL_DYNAMIC=FALSE  MKL_CBWR=COMPATIBLE,STRICT
   ```
   这一组就是 §3.4.1 实测能逐位复现的设置，一个都不要省、不要换（`-B` 和 `PYTHONDONTWRITEBYTECODE` 保证不往 v7 树里写 `__pycache__`）。标准输出和标准错误写到 `<workdir>/<name>/console.log`。任一子进程退出码非 0 就失败，并打印它 console.log 的最后 40 行。
4. **比较**：`compare_runs(<workdir>/v7, <workdir>/full)`（§3.4.5），结果写 `<workdir>/dual-tree-report.json`，打印汇总。父进程不导入 `po_jepa`，所以这个 JSON 用脚本里自己的小函数写，行为和 `cache._write_json` 相同（`sort_keys=True, indent=2, ensure_ascii=False, allow_nan=False`，末尾换行，目标已存在就报错，先写 `.partial` 再换名）。
5. 不删 `<workdir>`（留着给审核看）。

#### 3.4.3 子进程（`--worker`）做什么

按顺序：

1. 设环境变量：`PO_JEPA_PROTOCOL=v7`、`PO_JEPA_DATASET=van_der_pol:40`、`PO_JEPA_UPDATES=2000`、`PO_JEPA_SEED=1703`（和 `smoke_v7_cpu.py` 自己设的值相同；必须在导入任何 `po_jepa` 模块之前设，`po_jepa.datasets` 在导入时读一次环境变量），`PO_JEPA_AC_CHECKPOINT=<--ac-checkpoint>`。
2. 去掉 `sys.path[0]`（脚本所在的 `po-jepa-full/tests`），把 `<T>/src` 插到最前面。
3. `import torch; torch.set_num_threads(THREADS)`，断言 `torch.get_num_threads() == 1`，且 `WORKER_ENV` 的 7 个变量都在、值相同（防止有人绕过父进程直接调 `--worker`）。
4. `import po_jepa`，断言 `po_jepa.__file__` 在 `<T>/src` 下。
5. `from po_jepa.runtime import workflow`；调一次**真的** `workflow.verify_bundle()`（在 smoke 把它换掉之前），记下返回的 SHA。v7 树核的是 v7 自己的清单，新树核的是 §3.2 重算的清单；任一失败子进程就失败。
6. `from po_jepa import ac_baseline`；`ac_baseline.OFFICIAL = ac_baseline.ACSpec(width=64, depth=2, heads=4, mlp_ratio=4.0)`（§3.4.4 的缩小规格，写成脚本里的常量 `REDUCED_OFFICIAL = dict(width=64, depth=2, heads=4, mlp_ratio=4.0)`）。必须在第 7 步之前打（`comparison._ac_parameter_counts` 有 `lru_cache`，第一次调用就定下了）。
7. 用 `importlib.util.spec_from_file_location` 从 `<T>/tools/smoke_v7_cpu.py` 载入模块（这样它的 `ROOT` 就是 `<T>`），把 `sys.argv` 设成

   ```
   smoke_v7_cpu.py --system van_der_pol --trajectories 40 --features-root <features> --output <output>/smoke
                   --updates 20 --seed 1703
                   --jobs po_jepa_full,po_jepa_no_consistency,matched_transformer,identity,vjepa2_ac_small,vjepa2_ac
   ```

   然后调 `module.main()`。条件顺序就是 `v7jobs.JOB_CONDITIONS` 的顺序，两棵树相同（6 个任务在同一进程里依次跑，前一个任务可能改变全局随机状态，所以顺序不能变）。`--updates 20` 时 smoke 的缩小配置是：20 步、验证间隔 10（第 0、10、20 步验证并存检查点）、`lr_warmup_updates=1`、`consistency_warmup_updates=1`、一致性测量间隔 2、提前检查关掉、标定预训练 2 步加 2 批。`--jobs` 模式下 smoke 对每个条件调 `v7jobs.run_job`，对 identity 以外的条件再调一次只评测的 `run_job(..., training_run=…)`（目录名 `<条件>-evaluate`）。
8. 检查 `sys.modules` 里所有 `po_jepa` 开头的模块，`__file__` 都在 `<T>/src` 下。
9. 用本树的 `po_jepa.runtime.cache._write_json` 写 `<output>/worker.json`：`tree`、`po_jepa_file`、`po_jepa_modules`（相对 `<T>` 的路径列表）、`verify_bundle_sha256`、`smoke_v7_cpu_sha256`、`ac_reduced_official_spec`、`ac_checkpoint_sha256`、`torch_version`、`threads`、`python`、`seconds`。

**不改** `smoke_v7_cpu.py`，也不在脚本里另抄一份它的补丁。

#### 3.4.4 官方规模 AC 在 CPU 上怎么办

`smoke_v7_cpu.py` 本身没有给 vjepa2_ac 的 CPU 办法：`ac_training.build` 要 `PO_JEPA_AC_CHECKPOINT` 指向官方的 `vjepa2-ac-vitg.pt`，然后在 24 层、宽 1024、约 3.05 亿参数的模型上训练。这台机器上没有官方权重；即使有，参数、梯度和 Adam 状态就约 5 GB，一步训练的输入是 4 个片段 × 8 帧 × 258 个 token，加上 24 层的激活会超过 15 GB 内存；按算量估计每步要几分钟，560 个评测窗口还要逐帧滚动到 12 步，总共要很多小时。所以双树对照用缩小的“官方”规格，两棵树用同一个补丁、同一份假权重，走的代码路径和正式运行相同（`build` → `load_official` → 学习率 1e-4 的微调 → 检查点 → 评测），只是尺寸小：

- 规格 `ACSpec(width=64, depth=2, heads=4, mlp_ratio=4.0)`，参数 282,048（vjepa2_ac_small 是 width=64、depth=1、mlp_ratio=2.0 的 215,552，两个条件仍然不同）。
- 假权重（`--make-ac-checkpoint <path> --tree <v7>`，子进程，环境变量同 §3.4.3 第 1 步，路径同第 2 步）：`torch.manual_seed(0)` 后构造 `ac_baseline.ACPredictor(ACSpec(**REDUCED_OFFICIAL))`；取 `core.state_dict()` 里除 `action_encoder.*` 以外的全部项；再按顺序补 `action_encoder.weight = randn(64, 7)`、`action_encoder.bias = zeros(64)`、`state_encoder.weight = randn(64, 7)*0.02`、`state_encoder.bias = randn(64)*0.02`、`extrinsics_encoder.weight = randn(64, 6)*0.02`、`extrinsics_encoder.bias = zeros(64)`（官方的这三个编码器输入维是 7、7、6）；每个键前面加 `module.backbone.`（`load_official` 会依次去掉这两个前缀）；存成 `{"predictor": {...}}`，先写临时文件再换名。已在 v7 树上按这个做法端到端跑过（1 线程）：vjepa2_ac 的训练、评测、只评测重跑都完成，检查点 `info.official_load` 记 `loaded: 30`、替换 6 项，`info.parameters` 是 282,048。
- 官方规模的数值等价不在这里核：代码和 v7 逐字节相同，真实检查点上的等价核对在 GPU 机器上随 D4 做（07 §5.3）。

#### 3.4.5 比较什么、怎么比

`compare_runs(a, b, *, conditions=JOB_ORDER, updates=20)`，`a`、`b` 是两个子进程的输出目录。`JOB_ORDER` 就是上面的 6 个条件顺序。下面路径里 `J = smoke/jobs/<c>`，`T = J/training/<c>`，`E = J/evaluation/<c>`，`R = smoke/jobs/<c>-evaluate/evaluation/<c>`。

**怎么判相同**：JSON 里的值用 `json.dumps(x, sort_keys=True, ensure_ascii=False)` 规范化后比较字符串。Python 写 JSON 的浮点数是最短往返表示，所以字符串相同等价于 float64 逐位相同，也能分出 `-0.0` 和 `0.0`、`1` 和 `1.0`。报告不同之处时把两边的浮点数用 `float.hex()` 写出。张量：键列表（含顺序）、dtype、shape 相同，且 `t.detach().cpu().contiguous().reshape(-1).view(torch.uint8)` 的字节相同（先 `reshape(-1)`：0 维张量不能直接 `view(torch.uint8)`，会报错）。

| 项 | 文件 | 比的内容 | 每棵树的数量 |
|---|---|---|---|
| 子进程身份 | `worker.json` | 两边 `tree` 不同、各自的模块都在自己的树里；`threads`、`torch_version`、`smoke_v7_cpu_sha256`、`ac_reduced_official_spec`、`ac_checkpoint_sha256` 相同 | 1 |
| 标定 | `smoke/calibration.yaml`；`smoke/calibrate/sigma_z.json`；`smoke/calibrate/calibration.json` | yaml 逐字节；sigma_z.json 整份；calibration.json 去掉 `v7_calibration_file`、`note`（含绝对路径）后整份 | 3 |
| 任务完成 | `J/COMPLETE.json` | 两边都存在 | 6 + 5 |
| 初始权重哈希 | `J/report.json` 的 `initial_model_sha256` | 相同；5 个训练条件必须是 64 位十六进制，identity 必须是 `null` | 6 |
| 每步记录 | `T/updates/0001.json`…`0020.json` | 两边都恰好有 `updates` 个文件；每个文件比 `completed_updates`、`queries`、`losses`、`grad_max_abs`、`grad_norm_before_clip`、`learning_rate`、`raw_predictions`、`raw_target`、`phi_calls`、`consistency_gradient` | 5 × 20 |

**明确不比**的字段和文件（它们含耗时、绝对路径或源码 SHA；源码 SHA 在 S08a 以后会合法地变化，比较器要在 S08a、S10 原样复用）：任何 `seconds`、`update_and_observer_seconds`、`gpu_memory`；`provenance`、`checkpoint_provenance`、`checkpoint_sha256`、`checkpoint`（评测行里的检查点身份含验证耗时）、`source`、`sources`；`preregistration.json`、`registration.json`（训练目录里的）、`runtime.json`、`job.json`、`preflight/`、`source-collections/`、`trajectories/`、图（`*.svg`、`curves.json`）、`.pt` 文件的整体字节。

#### 3.4.6 耗时

实测（2026-11-08，这台机器，v7 树，1 线程，§3.4.2 第 3 步的环境，机器上同时还有 2 个同样的 1 线程进程）：

| 阶段 | 训练（20 步 + 3 次验证） | 评测（560 行 + 汇总） | 只评测重跑 | 合计 |
|---|---|---|---|---|
| 假特征（只做一次） | — | — | — | 25 s |
| 标定 | — | — | — | 15 s |
| po_jepa_full | 2.2 min | 3.7 + 2.8 min | 6.8 min | 16 min |
| po_jepa_no_consistency、matched_transformer | 没单独测，按 po_jepa_full 估 | | | 各约 16 min |
| identity | 不训练 | 约 7 min（估） | 不重跑 | 约 7 min |
| vjepa2_ac_small | 4.9 min | 6.1 + 2.7 min | 9.4 min | 23 min |
| vjepa2_ac（缩小规格） | 8.2 min | 9.5 + 2.8 min | 12.6 min | 34 min |

每棵树约 1 小时 50 分（训练很快，时间几乎都花在评测和只评测重跑上），两棵树并行跑，整次双树对照约 2 小时（比较本身读 2 × 6,160 行加检查点，不到 1 分钟）。每个子进程常驻内存约 1.4 GB。前台命令有时限，编写 agent 和审核 agent 都要把它放到后台跑，看 `<workdir>/<name>/console.log` 判断进度（`smoke_v7_cpu.py` 每开始一个条件打印一行 `training <c>` / `evaluating <c>`）。

同一棵树里，只评测重跑的 560 行和第一次评测逐位相同；同一棵树的两个独立进程（1 线程）之间，po_jepa_full、vjepa2_ac_small、缩小的 vjepa2_ac 从标定到评测汇总逐位相同（§3.4.1；另外两个 PO 类条件和 identity 用的是同一套训练和评测代码，没单独跑）。所以比较器如果在两棵树之间报了不同，不会是评测或进程本身的随机性造成的，要当成代码不同去查。
