## 3. 接口和产物

- `raw/<片名>/<uuid>/trajectory.h5`、`raw/<片名>/<uuid>/<left_serial>.mp4`：对象名 `{data.prefix}<h5>`、`{data.prefix}<left_mp4>`（03 §1）。
- `raw/<片名>/<uuid>/metadata.json`：`metadata.jsonl` 那一行去掉 `_name`、`_md5`、`_size`，原键顺序、缩进 2；不存在或内容不同就重写。
- `raw/<片名>/<uuid>/DOWNLOADED.json`（`cache._write_json`）：`{schema: droid_downloaded_v1, uuid, downloaded_at（UTC，到秒）, files: {本地文件名: {object, size, md5（base64，和 GCS 一致）, sha256}}}`。S05 的 `source` 从这里取两个 SHA-256。
- `raw/<片名>/_complete/<配置名>.json`（`cache._write_json`）：`{schema: droid_download_complete_v1, shard, config, config_sha256, splits_sha256, uuids（本配置在这片的回合，片计划顺序）, downloaded_sha256（与 uuids 一一对应）, code_commit}`。存在就什么都不做（12 §3）。

## 4. 实现上自己定的（规格没写死、可逆）

1. **三种失败分开处理**：传输失败（连接、5xx 等非 200 状态、响应体比 Content-Length 短、对象元数据格式不对）按 02 §1 重试（1 + 5 次，间隔 1、2、4、8、16 秒）；HTTP 404 不重试、直接失败（14 §3「404 直接失败」，03 §3「不跳过」）；下完的大小或 MD5 和对象元数据不同算一次坏下载，删 `.part` 重下，共 3 次（03 §2 第 3 条「最多 3 次」按总次数算），报错写明对象名。
2. **对象元数据地址**把整个对象名 URL 编码（斜杠也编成 `%2F`），只取 `fields=size,md5Hash`；每个文件只取一次。
3. **目标文件已在、没有 `DOWNLOADED.json`**（上次在两个文件之间中断）：先核大小和 MD5，对就直接用，不对就删掉重下。
4. **跳过规则**照 03 §2：有 `DOWNLOADED.json` 且两个文件大小都对就跳过，不重算 MD5；大小不对就先删 `DOWNLOADED.json` 再重下。`DOWNLOADED.json` 记的不是这条回合的这两个对象就报错（数据根被别的索引写过）。有 `RAW_DELETED.json` 就跳过，此时 `DOWNLOADED.json` 必须还在。
5. 每条回合开始时删掉目录里残留的 `.part`（03 §2 第 4 条）和 JSON 的 `.partial`，跳过的回合也删。
6. 片完成记录多记 `splits_sha256` 和 `code_commit`，方便 S05 核来源。
7. 片名不在本配置的片计划里就报错；划分和索引用 `splits.load_splits` 读（顺带核索引清单和四个文件）。
