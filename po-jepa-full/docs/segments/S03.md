## 3. 接口

- `compute_splits(episodes, data, episodes_sha256) -> dict`：episodes.jsonl 的全部行 → splits.json 的内容。先核入选行和配置一致（uuid 不重复、`reasons` 为空、`group` 和 `ood_labs` 一致、`steps ≥ min_steps`、同分布回合有场景号、`outcome` 合法），否则报错。候选场景不到 `id_test_scenes + val_scenes` 个、留出实验室入选回合不到配额都报错。
- `load_splits(data_root, config)`：先核索引清单和四个文件的 SHA、行数，再核 `schema == droid_splits_v1`（冒烟的 `droid_splits_smoke_v1` 拒绝）、`salt`、`config_keys` 和本配置一致、`episodes_sha256` 等于清单里 episodes.jsonl 的 SHA、`counts` 和列表长度一致、`train_failures ⊆ train_order`。
- `train_order(splits, data)`：本配置的训练顺序（见 §4 第 1 条）。
- `shard_plan(splits, data) -> {片名: [uuid…]}`：`train-000`… 再 `val`、`id_test`、`ood_test`。

## 4. 实现上自己定的（规格没写死、可逆）

1. **`train_order` 是完整训练顺序，`use_failures` 不进划分文件**。02 §7 原来把 `use_failures` 放进 `config_keys`、`train_order` 按开关去掉失败回合；但 04 §6、09 §3.1 要求同一数据根里能拿到“不受 `use_failures` 影响的完整训练顺序”，一个数据根又只有一份 `index/splits.json`。所以：文件里的 `train_order` 始终完整，失败回合另记在 `train_failures`（按训练顺序），`train_order(splits, data)` 在 `use_failures: false` 时去掉它们。主配置（`use_failures: true`）的训练集和原写法完全相同。02 §5 第 6、7 步、§6、§7 和 06 §1 已同步改。
2. **片按完整训练顺序切**，`use_failures: false` 的配置每片只列用到的回合；本配置训练顺序不到 N 条时 `shard_plan` 报错，不静默少用。真实数据上完整训练顺序 23,745 条、其中失败 4,196 条，去掉后 19,549 条，**不够 full 配置的 N = 20,000**（见交接遗留问题）。
3. **跨实验室场景号**只看入选回合（含留出实验室），`scene_id = −1` 不算；真实数据上不管看入选还是全部、含不含留出实验室，结果都是 4465064685、4823049285。
4. 所有排序键是 `(哈希, 原键)`：哈希相同（实际不会发生）时也确定。
5. `counts` 比 02 §7 的样例多 `candidate_scenes`、`train_failures` 两项。文件格式是 `cache._json_bytes`（键排序、缩进 2，约 1.3 MB）。写法和 index 的三个文件一样先写 `.partial` 再换名，重跑覆盖。
6. **S02 写的三文件清单**会被 `read_manifest` 认出并报错（“move the index away and rerun”）。升级办法：删掉 `index/MANIFEST.json` 重跑 `index`，会重新列表（要联网，几分钟）、`metadata.jsonl` 每行 MD5 都对上就不重下，再写划分和新清单。
