## 1. 目标与范围

S23b 登记了五个二阶场景（pendulum、bouncing_balls、wave、cart_pole、spring_chain），但 `tools/probe_actions.py`、`tools/plan_v7.py` 对它们直接报错，评测协议和 v8 任务表也没有它们。本段把这几处接上：定每个场景在探针里的距离（*_px 列）、在规划里的状态摘要和目标门槛，给 P1、P2 各三档物理参数，任务表能显式排二阶场景。

编码不动：二阶场景照 S23b 按单帧复制（dup）编码，特征里看不到速度。两帧（pair）编码等 S22 探针结果，在 S25b 接；所以 v8 任务表默认仍只排 7 个一阶场景，二阶场景要显式 `--scenes`。

不做：pair 编码；长时程、时间采样、空间采样的接入（S25c–e）；新任务（S25f）；二阶场景的 goal 采集策略。

第 6 阶段的拆分（Claude 定，Jerry 可以改）：S25a 本段；S25b pair 编码（等 S22 探针结果）；S25c 长时程接入（129 帧缓存、16–64 步滚动评测）；S25d 时间采样接入（非均匀帧时刻、tick 内部切换的动作）；S25e 空间采样接入（12–24 网格、SURROUND）；S25f 新任务（物理状态读出、反事实预测、模态频率对照）。

## 3. 约定（Claude 定，Jerry 可以改）

- **只比位置，不比速度。** 一帧画面只给位置，目标也只是一帧画面，所以探针的距离和规划的误差都只用构形（`configuration.py` 文件头的表）：

  | 场景 | 探针 *_px（整个构形 × 每单位像素） | 规划摘要 | 每单位像素 |
  |---|---|---|---|
  | pendulum | 摆锤 (sin θ, −cos θ) | 同左 | 80（摆杆 80 像素） |
  | cart_pole | (x, x + l·sin θ, l·cos θ) | 同左 | 36 |
  | spring_chain | 全部质点位置 | 第 0 个（受控）质点 | 48 |
  | bouncing_balls | 全部球的位置 | 第 0 个（受控）球 | 48 |
  | wave | u 的 16×16 池化场（不含 u_t、激振源），不乘像素 | 同左 | — |

  探针取整个构形，与 multi_particle 用全部粒子同一口径；规划取受控物体，与已有粒子类场景“受控小球位置”同一口径。摆和小车倒立摆要摆到目标的是摆锤，所以用摆锤（cart_pole 连小车一起）。wave 与 gray_scott 一样不计激振源（注入点）。
- **目标和成功判据不变。** 目标动作照粒子类场景均匀随机、每 2 tick 一段；真值规划的代价也用规划摘要（不像 push 那样要完整状态：二阶场景的摘要对动作不是处处平的）。“不动”在二阶场景里不是停住，惯性和振荡照样在走；成功判据照旧是“误差 ≤ 0.5 × 不动时的误差”。
- **目标门槛**：wave 按场的范数的 5%（同 gray_scott）；spring_chain 是 0.03，其余 0.15。依据是 `po-jepa-s25a/goal_gap_scan.py`（项目文件夹）在 8 tick 时域、每场景 40 个回合上第一次抽到的目标与“不动”之差：spring_chain 的中位数只有 0.041，最大约 0.055（弹簧硬，k = 16，K = 1.5，8 个 tick 只推开约 2 像素），0.15 一个都过不了；改成 0.03 后约 70% 第一次就过。其余二阶场景过 0.15 的比例 0.68–0.88，与 double_well 0.60、multi_particle 0.65、push 0.82 相当；wave 过 5% 的比例 1.00。
  - 顺带发现（没改，v7 口径）：landscape（多势阱）第一次过 0.15 的只有 3%，中位数 0.052，20 次重抽也约一半回合无效。
- **P1、P2 档位**（都在 `variants.PARAMS` 的范围里，S23a 的参数扫描覆盖）：

  | 场景 | P1（轻 / 标准 / 重） | P2（轻 / 标准 / 重） |
  |---|---|---|
  | pendulum | g_over_l 12 / 14 / 16 | damping 0.4 / 0.6 / 1 |
  | bouncing_balls | drag 0.4 / 0.6 / 1 | restitution 0.8 / 0.7 / 0.5 |
  | wave | speed 0.2 / 0.25 / 0.3 | damping 0.2 / 0.3 / 0.5 |
  | cart_pole | length 1.15 / 1.25 / 1.4 | mass_ratio 0.5 / 0.7 / 1 |
  | spring_chain | stiffness 19 / 21 / 25 | damping 0.2 / 0.3 / 0.5 |

  其余通用协议按 `variants.validate` 适用：五个场景都没有 P3（过程噪声）、P7（采集策略），wave 另外没有 P9、P10（没有光点）。标准档 53 格（pendulum、bouncing_balls、cart_pole、spring_chain 各 11，wave 9），轻档 48、重档 53；一阶 7 个场景的 82 / 75 / 77 格不变。P13 照“P1 + P4 + P8 同一档”给二阶场景组合档。
- **wave 的真值规划样本数 32**（`ORACLE_SAMPLES`）：本机 CPU 每 tick 实测 wave 11.5 ms，pendulum 0.8、bouncing_balls 2.6、cart_pole 2.0、spring_chain 0.1（double_well 3.9、push 25、gray_scott 67 作对照），只有 wave 比粒子类贵得多。
- **任务表**：默认场景不变（7 个一阶）；`--scenes` 可以写二阶场景，输出第一行注释写明它们按 dup 编码、看不到速度。等 S25b 定了 pair 编码再并进默认场景（那时特征目录要和 dup 的分开，免得混用）。

## 5. 遗留

- pair 编码（S25b）：探针的反事实终点、规划的目标和重规划画面都要多一帧前一帧（`frames_with_prev` 的约定；续算时前一帧就是上一个 tick 的状态）。现在的报告都标了 `tubelet: dup`。
- spring_chain 的动作效果小（8 tick 约 2 像素），规划在它上面区分度可能不够；要加大得改 S23a 的 K（改数据），没动，等 Jerry 定。
- landscape 规划目标约一半无效（v7 口径，§3），没动。
