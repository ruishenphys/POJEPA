## 3. 自己定的（可逆，Jerry 可以改）

1. 签名：06 §4 的 `prepared` 参数换成 `episode_arrays(prepared, uuids, source)` 给出的小表（每条回合只留行数、准备 JSON SHA、`action_<source>`、`state`），动作源由这张表定，`make_ac_clip_batch` 不再单传 `source`。原因：数据加载器的工作进程要带着它，整份准备数组（含 `state_all` 等）2 万条约 1 GB。
2. 每个窗口核对特征 JSON 记的 `prepared_sha256`、`rows` 等于这张表的（特征和动作出自同一份准备文件）；窗口编号必须等于 `window_id(uuid, d, s)`；s + d ≤ F − 1。
3. 加载分两半：`load_windows`/`load_ac_clips`（读行、核行 SHA、转 float32、取动作和状态，CPU，工作进程里）和 `assemble_training_batch`/`ac_clips_to`（搬到设备、调 `from_physical_segments`，主进程）。批内容只由（种子，步号）决定；第 w 个工作进程产出步号 ≡ start + w (mod n) 的步，DataLoader 轮流取，顺序即步号。
4. 端点秒数 = (s + d)·P，并核对它逐位等于 s·P + d·P（P = 1.0 时恒成立；换周期时不精确就报错）。
5. 来源：`source_files_sha256` = v7 的 7 个文件 + `src/po_jepa/droid/` 下全部 .py；证据角色由片清单的编码器身份定（`real_frozen_encoder` → `droid_training`，要求主特征的预处理 SHA 等于 v7 的；假编码器 → `synthetic_development_only`、`development_smoke`、四个 SHA 为 None）；各片编码器身份必须相同。
6. `comparison._tf_batch` 的检查：S08b 之前 `baselines.validate_inputs` 只许 2 维动作（最后一句），测试只容忍那一句、其余检查照跑；S08b 放宽后去掉这层容忍。
